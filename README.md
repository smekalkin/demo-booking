### Задача

В компании два офиса: Москва (Europe/Moscow) и Новосибирск (Asia/Novosibirsk), в каждом есть переговорные. Предыдущий разработчик написал API бронирования, и пользователи жалуются на ошибки. Код — в `app/Http/Controllers/BookingController.php`.

### Часть 1. Ревью

### Часть 2. Доработка

Исправьте `store` и `destroy` так, чтобы выполнялись правила:

- Брони одной комнаты не пересекаются. Встречи «впритык» разрешены: 10:00–11:00 и 11:00–12:00 — это не пересечение.
- Длительность от 15 минут до 4 часов, шаг 15 минут (10:00, 10:15…).
- Бронь целиком укладывается в рабочее время 09:00–20:00 по местному времени офиса, где находится комната. Клиент присылает время в ISO 8601 с любым смещением.
- Отменить бронь может только её автор.
- Понятные ошибки валидации (422).
- Других ограничений на даты нет.
- Feature-тесты на все правила выше.

Можно менять модели и миграции и добавлять свои классы. Методы `index` и `today` исправлять не нужно, их достаточно разобрать в ревью.

Бонус: при двух одновременных запросах на один слот может создаться двойная бронь. В основной части достаточно, чтобы брони не пересекались при последовательных запросах. Гонку исправьте или опишите в README, как бы вы это сделали.

## API

Все методы требуют заголовки `Authorization: Bearer <токен>` и `Accept: application/json`. Без `Accept` запрос без токена вернёт 500 вместо 401.

| Метод | Адрес | Что делает |
| --- | --- | --- |
| GET | `/api/bookings` | Мои брони |
| POST | `/api/bookings` | Создать бронь |
| DELETE | `/api/bookings/{id}` | Отменить бронь |
| GET | `/api/rooms/{room}/bookings/today` | Брони комнаты на сегодня |

Пример:

```sh
curl -X POST http://localhost:8000/api/bookings \
  -H "Authorization: Bearer anna-token" \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{"room_id": 1, "title": "Планёрка", "starts_at": "2026-11-02T10:00:00+03:00", "ends_at": "2026-11-02T11:00:00+03:00"}'
```

Автор брони определяется по токену, `user_id` в запросе не нужен и игнорируется.

Время принимается в ISO 8601 с обязательным смещением: `2026-11-02T10:00:00+03:00`, `2026-11-02T07:00:00Z`, `2026-11-02T07:00:00.000Z`. В ответах время в UTC.

Ошибки бронирования — `422` в стандартном формате Laravel:

```json
{
    "message": "Комната уже занята в это время.",
    "errors": {"starts_at": ["Комната уже занята в это время."]}
}
```

Отмена чужой брони — `403`, несуществующей — `404`.

Лог созданных броней пишется в `storage/logs/bookings.log`.

## Одновременные запросы на один слот

Проверка пересечений в `StoreBookingRequest` и вставка — разные запросы. Два одновременных запроса могут оба пройти проверку и оба вставить бронь.

Гарантию даёт PostgreSQL. В миграции `add_time_constraints_to_bookings_table` есть ограничение-исключение:

```sql
EXCLUDE USING gist (room_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&)
```

Две брони одной комнаты с пересекающимися полуинтервалами `[начало, конец)` не могут существовать одновременно, какими бы путями ни шли запросы. Правая граница не включена, поэтому встречи впритык разрешены. Для `room_id WITH =` в индексе GiST нужно расширение `btree_gist`, миграция его включает.

Что делает приложение:

- нарушение ограничения (`SQLSTATE 23P01`) превращается в ту же `422 «Комната уже занята»`, что и при обычной проверке;
- при одновременной вставке пересекающихся строк PostgreSQL может обнаружить взаимную блокировку (`40P01`) и прервать одну из транзакций. Вставка идёт в `DB::transaction(..., attempts: 3)`: Laravel повторяет транзакцию, и повтор получает обычное нарушение ограничения.

Проверка приложения перед вставкой остаётся: она даёт ответ без похода в ограничение в обычном, последовательном случае.

Как проверялось. Встроенный сервер PHP по умолчанию обрабатывает запросы по одному, поэтому гонку на `php artisan serve` не увидеть. Внутри контейнера был запущен сервер с воркерами:

```sh
docker compose exec -d -e PHP_CLI_SERVER_WORKERS=10 -w /app/public app \
  php -S 127.0.0.1:8002 /app/vendor/laravel/framework/src/Illuminate/Foundation/resources/server.php
```

На него отправлялось по 10 одновременных `curl` на один слот, 10 слотов за раунд:

| Вариант | Результат |
| --- | --- |
| Без ограничения, только проверка в приложении | до 9 броней на один слот |
| С ограничением, без повтора транзакции | одна бронь на слот, но 27 из 100 ответов — `500 deadlock detected` |
| С ограничением и повтором | 3 раунда, 300 запросов: одна бронь на слот, 30 × `201`, 270 × `422`, ни одного `500` |

`php artisan serve` переменную `PHP_CLI_SERVER_WORKERS`, переданную через `docker compose exec -e`, не подхватил — поэтому сервер запущен напрямую.

В тестах гонка моделируется детерминированно: `test_returns_validation_error_when_concurrent_request_takes_slot` вставляет конфликтующую бронь после валидации запроса, но до вставки.
