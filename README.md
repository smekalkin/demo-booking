## API

Все методы требуют заголовки `Authorization: Bearer <токен>` и `Accept: application/json`. Без `Accept` запрос без токена вернёт 500 вместо 401.

| Метод | Адрес | Что делает |
| --- | --- | --- |
| GET | `/api/bookings` | Мои брони |
| POST | `/api/bookings` | Создать бронь |
| DELETE | `/api/bookings/{id}` | Отменить бронь |
| GET | `/api/rooms/{room}/bookings/today` | Брони комнаты на сегодня |

Пример:

```sh
curl -X POST http://localhost:8000/api/bookings \
  -H "Authorization: Bearer anna-token" \
  -H "Accept: application/json" \
  -H "Content-Type: application/json" \
  -d '{"room_id": 1, "title": "Планёрка", "starts_at": "2026-11-02T10:00:00+03:00", "ends_at": "2026-11-02T11:00:00+03:00"}'
```

Автор брони определяется по токену, `user_id` в запросе не нужен и игнорируется.

Время принимается в ISO 8601 с обязательным смещением от `-14:00` до `+14:00`: `2026-11-02T10:00:00+03:00`, `2026-11-02T07:00:00Z`, `2026-11-02T07:00:00.000Z`, а также в формате ответов API (`2026-11-02T07:00:00.000000Z`). В ответах время в UTC.

Ошибки бронирования — `422` в стандартном формате Laravel:

```json
{
    "message": "Комната уже занята в это время.",
    "errors": {"starts_at": ["Комната уже занята в это время."]}
}
```

Отмена чужой брони — `403`, несуществующей — `404`.

Лог созданных броней пишется в `storage/logs/bookings.log`.

## Одновременные запросы на один слот

Проверка пересечений в `StoreBookingRequest` и вставка — разные запросы. Два одновременных запроса могут оба пройти проверку и оба вставить бронь.

Гарантию даёт PostgreSQL. В миграции `add_time_constraints_to_bookings_table` есть ограничение-исключение:

```sql
EXCLUDE USING gist (room_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&)
```

Две брони одной комнаты с пересекающимися полуинтервалами `[начало, конец)` не могут существовать одновременно, какими бы путями ни шли запросы. Правая граница не включена, поэтому встречи впритык разрешены. Для `room_id WITH =` в индексе GiST нужно расширение `btree_gist`, миграция его включает.

Что делает приложение:

- транзакция вставки сначала блокирует строку комнаты (`lockForUpdate()`), поэтому вставки в одну комнату идут по очереди. Следующая видит уже закоммиченную бронь и сразу получает нарушение ограничения;
- нарушение ограничения (`SQLSTATE 23P01`) превращается в ту же `422 «Комната уже занята»`, что и при обычной проверке.

Почему нужна блокировка, хотя ограничение уже есть: без неё одновременные вставки пересекающихся строк ждут друг друга на проверке ограничения, и PostgreSQL прерывает часть транзакций с взаимной блокировкой (`40P01`). Двойной брони при этом нет, но клиент получает `500`. Повтор транзакции (`DB::transaction(..., attempts: 3)`) это не лечит: при 10 конкурентах транзакция трижды подряд попадает во взаимную блокировку.

Проверка приложения перед вставкой остаётся: она даёт ответ без похода в ограничение в обычном, последовательном случае.

Пояс сессии PostgreSQL закреплён в `config/database.php` (`'timezone' => 'UTC'`). Laravel передаёт даты в базу строкой без смещения, и `timestamptz` читает её в поясе сессии; без этой настройки брони сдвинулись бы на сервере с другим поясом.

### Как проверялось

Встроенный сервер PHP по умолчанию обрабатывает запросы по одному, поэтому гонку на `php artisan serve` не увидеть, а `PHP_CLI_SERVER_WORKERS`, переданный через `docker compose exec -e`, он не подхватывает. Внутри контейнера запускался сервер с воркерами напрямую:

```sh
docker compose exec -d -e PHP_CLI_SERVER_WORKERS=10 -w /app/public app \
  php -S 127.0.0.1:8002 /app/vendor/laravel/framework/src/Illuminate/Foundation/resources/server.php
```

На него отправлялось по 10 одновременных `curl` на один слот, 10 слотов за раунд, 10 раундов — 1000 запросов на прогон:

| Вариант | Результат |
| --- | --- |
| Только проверка в приложении, без ограничения | до 9 броней на один слот |
| Ограничение, без блокировки комнаты | одна бронь на слот, но 27 из 1000 ответов — `500 deadlock detected` |
| Ограничение и повтор транзакции `attempts: 3` | одна бронь на слот, 44 из 1000 — `500` |
| Ограничение и блокировка комнаты (итоговый вариант) | два прогона, 2000 запросов: одна бронь на слот, 200 × `201`, 1800 × `422`, ни одного `500` |

Повтор транзакции сначала выглядел рабочим: на 300 запросах ни одного `500`. Ошибка проявилась только на 1000.

В тестах гонка моделируется детерминированно: `test_returns_validation_error_when_concurrent_request_takes_slot` вставляет конфликтующую бронь после валидации запроса, но до вставки, а `test_locks_room_before_inserting_booking` проверяет, что блокировка комнаты идёт раньше вставки.

### Миграция на существующих данных

Старый код мог насоздавать пересекающиеся брони, и тогда миграция упадёт на создании ограничения (`could not create exclusion constraint`) и откатится целиком. Перед миграцией конфликты нужно найти и разрешить вручную:

```sql
SELECT a.id, b.id, a.room_id, a.starts_at, a.ends_at, b.starts_at, b.ends_at
FROM bookings a
JOIN bookings b ON a.room_id = b.room_id AND a.id < b.id
WHERE a.starts_at < b.ends_at AND a.ends_at > b.starts_at;
```

Время старых броней переводится `AT TIME ZONE 'UTC'` как есть. Если клиент присылал не UTC, старый код уже отбросил смещение, и исходный момент из базы не восстановить.
